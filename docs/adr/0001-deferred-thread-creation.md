# 新建会话延迟落库与草稿槽

新建对话曾经「点击即写库」，侧栏与搜索被无消息的空「新对话」污染，重启还会残留。决定改为草稿态延迟落库：新建只是渲染层的草稿——不写事件表、不进会话列表；发出首条消息时才由对话服务的原子路径一次性完成「模型校验 → 创建会话（短标题）→ 写用户消息事件 → 启动 Run」，模型校验前置保证失败零落库。草稿按模式与工作区归属分槽持久化，临时会话与每个项目各自一槽、互不覆盖。由此侧栏与数据库天然不存在空会话，无需任何列表过滤闸门。

## Considered Options

- **立即创建（原行为）**：点新建即写库。被否：空会话堆积、搜索互相误命中、重启残留脏数据。
- **ZCode 式预热 deferred 会话 + 列表闸门**：预创建不落库的内存会话，用「deferred 标记 + 三处列表过滤」挡在侧栏外。被否：该复杂度为多 pane / 多窗口架构服务——那里草稿有多个并发创建入口，需要协调器收敛；本应用单活动会话，草稿天然只有一个创建入口，把创建推迟到首发即可，deferred 标记、预热回收与闸门均无必要。

## Consequences

- 线程创建通道仅剩服务内部调用方，渲染层不再直接使用；历史遗留空会话由一次性迁移清理。
- 首发后 Run 启动失败不回滚（用户消息先落事件表是仓库原则，会话保留可重试）。
- 行为边界与拆票见 `docs/draft-session/`（spec 与 issues）。
