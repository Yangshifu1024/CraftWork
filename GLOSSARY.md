# CraftWork Glossary

This file is the repository's authoritative domain vocabulary. Use these terms in issues, ADRs, code comments, and commit messages; do not drift into synonyms.

## Product and Modes

| Term | Definition |
| --- | --- |
| CraftWork | A desktop agent: a Rust domain kernel carries all domain logic (agent loop, tools, policy, storage, keys) and the renderer is a React UI |
| Code mode | The developer workbench: workspace, code editing, shell, git, and diffs |
| Work mode | The document workbench: text-level read and preview for Word / Excel / PDF; no git, diffs, or shell |
| Mode accent | The global accent color that switches with the UI mode: Code is blue, Work is yellow (`--craft-mode-*` semantic tokens); drives the sidebar mode-switcher selected state and all primary buttons (overrides `--craft-brand`), with separate values per light/dark theme |
| Workspace | A project root the user picks locally, independent of mode; one or more source folders can be mounted, and the same project opens in both modes |
| Source folders | Directories mounted into a workspace; the first is the primary folder, the rest are additional folders, and all are inside the agent's accessible scope |
| Primary folder | The workspace's first source folder and the session's working directory (`workspaces.path`); Git and environment context apply only to it |
| Additional folders | Source folders in a workspace other than the primary; path tools may resolve to them with "existing-first" semantics, while Git operations support only the primary folder |
| System temp dirs | The OS temp directories (`std::env::temp_dir()`, plus `/tmp` on Unix) — an **implicit accessible root** outside the workspace (D28): **absolute** paths in tool arguments may land there, relative paths always stay in the workspace; risk follows the tool's base level (read R0, write R1) and is never escalated to R3 for being outside. Not part of the workspace — excluded from `RunEnv roots`, additional-folder listings / Git / skill scans, and unknown to the renderer's file panel and attachments; `git_*` tools return a readable error at assessment time when given a temp-dir path |
| Edit source folders | The edit entry for an existing project's source folders (sidebar project context menu): add/remove additional folders, set one as primary (moved to first). Shares validation rules with the create-project dialog; switching the primary folder is blocked while a session with a bound git worktree exists. The affected surface (RunEnv roots, prompt folder listing, Git primary-only, skill scans, worktree origin) is documented on `workspace_replace_folders` |
| Workspace trust | The workspace's two states: trusted / restricted; new projects default to restricted. The create-project dialog does per-folder trust confirmation and creates with the chosen tier |
| Create-project dialog | The entry for creating a project workspace: name (derived from the primary folder name when empty, duplicate names auto-suffixed), multiple source folders (first is primary), and a per-folder "trust this folder?" confirmation before submit (trust is not persisted); on confirm the workspace is created trusted and entered as a draft |
| Thread (session) | One continuing conversation, persisted by the backend events table and rendered by subscribing to events; belongs to Code or Work mode |
| Draft | A session intent that has not sent its first message: nothing written to the events table, invisible in the session list and search; content survives restarts, and the thread is only created when the first message is sent |
| Draft slot | Drafts bucketed by mode and workspace ownership: the scratch session and each project get their own slot, never overwriting each other; a slot holds unsent text, attachments, and the model reference |
| Run | One execution from a sent message to agent completion or failure; a session allows only one run at a time |
| Plan mode | The composer-top send toggle: when checked, the round proceeds as read-only investigation and produces a step-by-step plan for user confirmation. Double insurance = plan instructions injected into the system prompt + the plan-mode hard gate: under the **graded tier**, every `mutates` tool in plan mode (by the tool spec's `mutates` flag, not risk level — `fs_write` is R1, and a "≥R2" check would miss exactly the writes that matter) is intercepted before approval, returning only an error result with a way out; protocol tools, read-only tools, and `todo_write` pass. **The free tier disables the gate** (free = allow everything; the gate was once the only place that ignored the tier), but `exit_plan`'s unconditional approval is tier-independent — the review card still appears on free. Approval tiers themselves are unchanged (plan-mode permissions equal the tier; the old "R1+ always asks" rule is gone). **Auto-enter (D32)**: in a non-plan-mode run, after 2 distinct files are modified a soft reminder announces the rule, and the write to a 3rd distinct file is intercepted before execution and the run auto-enters plan mode (five exemptions in D32); after `exit_plan` approval implementation continues and the plan text is persisted as usual. Once a plan exists the user clicks "approve and execute" (unchecks the toggle and sends a fixed confirmation message) or types adjustments. See D8 / D32 and the plan-mode hard gate comments in `runner.rs` |
| git worktree | The composer-top send toggle: when checked, sending creates an independent git worktree under the data directory (`<data dir>/worktrees/<session id>`, branch `craftwork/<session shortcode>`) and binds it to the session; session-level binding, cannot be unbound, and all subsequent file / command / Git operations of that session run inside the worktree (RunEnv primary folder switched), leaving the primary folder untouched; cleaned up on session delete, with a warning in the delete dialog when unmerged changes exist. Available only for project workspaces + git repos + Code mode |
| Scratch session | A regular session bound to the app's built-in temp directory (data dir `workspace/default`, `purpose = conversation`); works out of the box with the same capabilities as workspace sessions, file operations limited to the built-in directory; right-click the sidebar "scratch sessions" group header for one-click cleanup (all current-mode, non-archived sessions deleted; running / approval-pending ones skipped) |
| Steering | User instructions queued while a session is running: merged into the next model request after the current tool batch ends, and re-spawned as a new run automatically when the run finishes. Queued-but-undelivered messages show a "pending delivery" marker in the timeline; `steer.delivered` receipts remove the marker on delivery or finish-time drop (the consumption point also starts a new assistant message, so subsequent output renders below the steering bubble) |
| Steering acknowledgement | The visible response the model gives first in the round where steering was merged: states what the input changed before continuing. A batch of steering merges into one sentence; on conflict the last one wins. The acknowledgement is plain text, not a dedicated receipt part (never call it "ack" or "received") |
| EnvContext | The environment snapshot collected at run start: date / platform / shell + git summary + instruction files (the two AGENTS.md levels); any failure degrades to omission without blocking the run |
| Skill | An instruction package whose directory entry point is a SKILL.md (markdown body + optional helper scripts / assets): placed by the user under user-level roots (`~/.craftwork/skills`, `~/.agents/skills`) or workspace-level roots (`<workspace>/.craftwork/skills`, `<workspace>/.agents/skills`), or installed via the skill store (plugin skills expose as `plugin:skill` qualified names with bare names as aliases; manual skills win name conflicts); rescanned every run to inject the "available skills" listing, and the model loads the body via the `skill` tool by name (D11); `/name [args]` in the composer invokes explicitly (the message stream shows the raw capsule header and the model history is replaced by a steering prompt). Directory priority, budgets, and loading rules: `crates/craft-tools/src/skills.rs` module header; store cache and version pointers: `craft-marketplace` module headers (D12) |
| Skill Store | The management UI for browsing, installing, upgrading, rolling back, and uninstalling marketplace plugin skills (Settings → Skills, "local skills / skill store" tabs): no market source is pre-configured, with a one-click built-in recommended source; install / upgrade / disable / uninstall take effect in the next conversation turn (D12) |
| Subagent | The capability of dispatching a well-bounded subtask to another agent loop (D15): a subagent has its own session history, tool surface, model, and context, and hands its conclusion back to the main agent. Model-visible tools are `agent_spawn` / `agent_wait` / `agent_list` / `agent_close`; built-in types are `general` (writable, executable) and `explore` (read-only, including web_fetch), plus user-defined types. Dispatch defaults to background (immediate receipt, report injected at terminal state — D31); explicit `run_in_background=false` gives a blocking foreground wait. Subagent-thread carrier, the four tools' boundaries, and cancel cascades: D15 and the `crates/craft-agent/src/subagent.rs` module header |
| Agent profile | The effective per-dispatch agent configuration (`ResolvedProfile`): type, display name, role prompt, tool allow-list, model, iteration cap, and whether instruction files are injected. Resolved by `subagent::resolve_profile` — built-in types look up built-in profiles with adjustable defaults, custom types look up user definitions. The Runner consumes only this shape and never distinguishes "custom or not" |
| Custom agent | A user-created subagent definition in Settings → Subagents: name (the `agent_type` value at dispatch), description, role prompt, tool surface in three tiers (read-only / all / named list), default model, iteration cap, enable state. Definitions live in the dedicated settings key `subagent.profiles` and are selected by name at dispatch; the effective profile snapshot goes into `threads.agent_profile`, so later edits or deletes do not affect history. Resolution and fallback order: `subagent::resolve_profile` (D15 extension) |
| Subagent thread | The session row created in `threads` per subagent dispatch (`parent_thread_id` non-empty): events, snapshots, compaction, usage, and logs are all reused; excluded from sidebar and search, deleted with the parent; reached in the UI via the subagent card's "open in side panel" or the panel's subagent list, as a read-only detail tab |
| Subagent card | A `kind="subagent"` part in the parent conversation: type badge + name + dispatch summary + duration + tool count + status, expandable to the conclusion; multiple events of one `partId` (running, intermediate, terminal) merge into a single card (intermediate events advance iterations and tool counts per tool call) |
| Foreground / background dispatch | The two dispatch forms: foreground = the main agent blocks for the result, returned as the tool result; background = an immediate start receipt, with the report injected into the parent history at terminal state (next iteration while running, auto-wake when idle). **Dispatch defaults to background** (D31): omitting `run_in_background` means background, explicit `false` means foreground — under the serial tool loop a foreground default would queue "multiple dispatches in one reply" waiting for terminal states, making parallelism illusory. Background dispatch is only a dispatch form, never "background subagent"; strictly distinct from "background command task" |
| Background command task | A command started by `shell_exec` with `run_in_background=true`: the tool call returns a task id and output file path immediately while the process keeps running; at terminal state a short notification is injected into session history and idle sessions are woken. A foreground command that times out (first word is not `sleep`) also moves to background instead of being killed. Companion tools: `bash_output` (read output tail) and `kill_shell` (kill the group). Timeout-to-background, notification delivery, and idle wake: `crates/craft-agent/src/shell_tasks.rs` module header. Not the same as subagent background dispatch: `agent_wait` waits only for subagents, and background command tasks need no waiting tool |
| Wait tool | A timer wait interruptible by events and the user (D21): sleeps `duration_ms` (1s–600s, default 30s), or returns early when a background task completes / a subagent reports / user input arrives (reports only the wake source; event bodies go through the existing injection point); the user can "skip wait" — the run continues and the model immediately re-verifies the wait purpose (`purpose` argument). Boundaries with the other two waits: for background tasks, end the turn and wait for the notification (no wait tool; shell `sleep` is pre-rejected); for subagents use `agent_wait`; wait waits only for time and event signals |
| Marketplace | A user-added skill distribution source: a git repository whose manifest declares the plugins it contains; the form is auto-detected on add (market-manifest repo / single-plugin repo / bare skill collection). The recommended market source is a build-time candidate list; the source itself still requires user confirmation to add |
| Plugin | The skill distribution unit inside a marketplace: a self-contained directory (plugin manifest + one or more skills with helper scripts); other plugin components are not loaded — commands map to skills, while hooks / agents / MCP declarations are only noted on the detail page |
| Installed manifest | The persistent record of installed plugins: `plugin@market` identity, current version, retained historical versions, install path, and origin; SQLite is the source of truth |
| Version pointer | The record in the installed manifest pointing at the currently active version directory; upgrade = write the new version directory then switch the pointer, rollback = switch back to a retained version (last 3 kept) |
| Part | A structured block inside a message: text, reasoning, tool, approval, todo, error, draft, etc. |
| Turn Navigator | The vertical rail on the left of the message stream: one tick per real user input, hover shows that user message, click scrolls to it, and the tick for the viewport's turn highlights. Appears only with ≥2 entries and a conversation container ≥864px; plan feedback, subagent-report anchors, and the approved-plan fixed confirmation message are excluded (they are not user-initiated input). Rules: `src/renderer/src/lib/turn-nav.ts` module header and `EXCLUDED_VIA` |
| Snapshot | The complete session state obtained by reading events by `thread_id` and grouping by `message_id` |
| System notifications | Three desktop notifications (approval pending / completed / failed): sent only while the window is unfocused, gated by the Settings "system notifications" switch (read live) |
| Input prediction | After a normal turn ends, the backend pre-computes a "next suggestion prompt" from session context and the user's input history: shown as ghost text in the composer after 5 seconds of inactivity, applied with Tab, ignored if the user types; Settings → Personalization, on by default; best-effort semantics (silent failure, no event rows), in-memory transient cache |
| Network config | The outbound proxy configuration in Settings → Network: system proxy (default) / none / custom, applied uniformly to all app network requests (model calls, provider probes and fetches, skill store downloads, and web_fetch); local network ranges always connect directly (built-in exclusions under custom proxy, not configurable); `craft-core::network` is the single resolution point and new outbound requests must not bypass it (D14) |
| GitHub acceleration | The prefix-rewrite mechanism for github.com / raw.githubusercontent.com access: a switch + prefix URL (default gh-proxy.com, replaceable with any similar service); rewritten requests still obey the proxy mode, and on acceleration failure it falls back to the original URL and retries once (acceleration first, proxy as fallback) (D14) |

## Risk and Approvals

| Term | Definition |
| --- | --- |
| Risk level | R0 read / R1 workspace write / R2 execute / R3 network or out-of-bounds / R4 destructive; arguments can escalate risk |
| Approval tier | Graded / free; the tier is an input to the policy engine and does not change risk grading itself. The historical strict / read-only tiers are removed (superseded by graded and plan mode respectively); stored legacy values fall back to graded |
| Free tier | The only tier that allows everything (including R4); switching requires the "capability list + I understand the risks" confirmation gate, after which the safety net degrades to the approval rows and tool-call events alone |
| Grant scope | `once` / `session` / `workspace`; R3, R4, and restricted workspaces never get permanent grants |
| Restricted workspace | A workspace state where R3 is rejected outright, R1/R2 ask every time, and existing grants do not apply |

## Models and Providers

| Term | Definition |
| --- | --- |
| Provider | The access configuration for a group of model services: protocol, endpoint, and key; models under one provider share the key |
| Provider enable toggle | The provider-level switch: disabled providers remove all their models from the selector, and calls are intercepted by the model client factory with "model disabled"; historical session references are unaffected and still resolve for display |
| Model enable toggle | The per-model switch: disabled models disappear from the selector and calls are intercepted likewise; configuration is kept and re-enabling restores availability |
| Fetch models | Pull the model list from the provider endpoint and merge by ID with dedupe: OpenAI-style `GET {endpoint}/models`, Anthropic `GET {endpoint}/v1/models`; existing entries are not overwritten, additions default to enabled with `source = fetched` |
| Model catalog | The build-time snapshot of models.dev (`catalog.json.gz`), used only as the candidate list for adding providers; provider logos are downloaded and cleaned at build time into renderer assets, and most providers prefill the endpoint on import |
| Model reference | The precise `providerID/modelID` form; the same model ID may appear under multiple providers |
| Protocol | Only three: `openai`, `anthropic`, `openai-compatible`; native Google / Gemini protocols are not integrated |
| Failover | Model switching limited to 429, 5xx, timeout, and connection failures; mid-tool-call failures never fail over |
| Context usage | The `input + output` tokens of the most recent main-conversation request, overwritten (not accumulated) each turn; the composer's usage control measures first and estimates as fallback (session total + body length ÷ 4), click for the detail breakdown |
| Context compaction | Early messages are summarized when history exceeds 70% of the model window; the summary is persisted as a `context_summary` event |

## Architecture and UI

| Term | Definition |
| --- | --- |
| Domain kernel | The agent loop, tools, policy, SQLite, model client, and keys all execute in domain crates (`craft-core` / `craft-store` / `craft-policy` / `craft-agent` / `craft-model` / `craft-tools` / `craft-doc`); domain crates are plain Rust modules without Tauri, and only the app shell (`src-tauri`) touches Tauri APIs |
| Renderer | React 19 + zustand + Tailwind v4 UI; holds no Node capabilities, loads no remote pages, and reaches system operations only through the channel table |
| tauri-bridge | The renderer implements the central channel table as Tauri `invoke` calls (`lib/tauri-bridge.ts` provides the `window.craftwork` surface) with no business logic |
| channels | The single exit for renderer system operations; method signatures are defined in `src/shared/channels.ts`, wired in sync across `channels` / `tauri-bridge` / `src-tauri` dispatch |
| Event | One row in the `events` table, the session's source of fact, monotonic `seq` per thread; the type table is an internal contract |
| Recorder | `craft-store`'s `recorder.rs`: the single exit for event writes and broadcasts, one call doing seq allocation, persistence, and broadcast |
| Esc unwind chain | Window-level shortcuts live in renderer hooks; Esc unwinds one layer at a time: overlay first → double-Esc on a running session to confirm stop (sharing the armed state with the stop button); not intercepted during IME composition |
| System prompt cache layers | Three blocks: identity (no cache marker) / stable (identical across sessions) / dynamic (stable within a session) |
| Side panel | The panel right of the conversation column (`SidePane`), a "pinned views + dynamic tabs" model: pinned views are files / subagents (always present, not closable), dynamic tabs are the plan (singleton) and subagent details (multiple allowed), appearing only when opened, closable, surviving across sessions, cleared on restart. Three postures: closed (renders nothing — the old 36px icon rail was removed by D22; the open entry is the toggle at the session header's right end), variable-width placeholder column (default 380px, draggable 280–760px), and maximized drawer (covers the conversation area but keeps the placeholder width; the conversation column does not reflow). Width is session-scoped posture, not persisted across restarts (D17). Postures and tab rules: `src/renderer/src/components/panel.tsx` and the pane state in `store/app.ts`; width sources: `lib/resize.ts` |
| Session sidebar | The session navigation rail on the window's left edge (`Sidebar`), default 264px, draggable 200–480px; `⌘B` collapses it into a 36px expansion strip (a visible recovery entry), and the collapsed state occupies no layout — width and collapsed state are session-scoped posture, not persisted across restarts (D17). Ranges and snapping: `src/renderer/src/lib/resize.ts` |
| Resize handle | The width control on both rails' edges (`ResizeHandle`): 4px hit area, 2px vertical line on hover/focus/drag, `role="separator"` keyboard adjustment (←/→ ±8px, Home/End, double-click reset). While dragging only CSS variables are written, never React state; releasing past min 24px snaps to collapsed (D17) |
| Session-scoped posture | UI state describing only "how it looks right now" with no information loss when discarded (rail widths, collapsed states, maximization, dynamic tabs); contrast with **preferences** (font size, theme, persisted into `settings`). Criteria in D17 |
| Shell environment | Where command subprocesses get their environment (D18): a fresh data directory defaults to the login shell; users may switch or explicitly choose "none" (minimal environment). With a shell selected, its **startup profile** (`.zshenv`/`.zshrc`/`.bash_profile`/`config.fish` — rc files in Unix jargon, same naming tradition as `.vimrc`) runs before each command, and its environment is handed to the subprocess after secret-like keys are stripped by blacklist. The single strip rule lives in `craft_core::shellenv::is_sensitive_key`, shared by `shell_exec` / runtime detection / MCP stdio. Prompts inject variable names only, never values. The selected shell also picks the **executor** — the interpreter of commands; platform defaults apply when none is selected (D25). Capture, stripping rules, and the four shared paths: `crates/craft-core/src/shellenv.rs` module header |
| System tray | The OS's persistent background entry (macOS menu bar top-right / Windows notification area): shows/hides the main window, running and approval-pending status, quit. The tray is not a second window and carries no session content. Scope and degradation: `src-tauri/src/tray.rs` module header (D20) |
| Close to tray | Clicking the window close control hides the main window without quitting: runs, background commands, and MCP keep running. Distinct from **minimize** — minimizing keeps the taskbar / Dock entry, while close-to-tray leaves only the tray entry (macOS keeps the Dock icon). The "quit when closing the window" setting restores the old semantics |
| Tray status | The tray menu's read-only top counters "running / approval pending", deduplicated by main session: a subagent's runs and approvals count toward the parent, one count per session; running = has an unfinished run (including awaiting approval), pending = has an undecided approval. Both can point at the same session |
| Tray red dot | The Windows tray icon's approval-pending marker: a plain red dot (no number) while approvals are undecided, gone at zero. macOS does not use a tray red dot — pending approvals surface via the Dock badge, tray menu status, and system notifications |
| Single instance | Only one app process runs at a time: a duplicate launch does not spawn a process but raises and focuses the existing main window |
| Dock badge | The numeric badge on the macOS dock icon: the count of sessions needing attention = unread or approval pending (deduplicated by main session, archived excluded); Windows does not use a taskbar badge in this release |

## Storage

| Term | Definition |
| --- | --- |
| Data directory | `~/.craftwork`: `craftwork.db`, `keys.json`, `attachments/`, `workspace/default` (built-in scratch session directory), `logs/`; `CRAFTWORK_HOME` isolates it |
| keys.json | The per-provider key file; directory 0700, file 0600; never enters logs, the database, or export packages |
| Storage usage | The data directory's disk footprint, **split in two parts, never merged into one number**: **inside the database** (rows and index pages in SQLite, not released without VACUUM) and **data-directory files** (files outside the database: attachments, logs, background outputs, worktrees, plan texts, store cache). "Per-session usage" is an **ownership estimate** (event payload bytes + files named by session id), not the session's exclusive bytes. See D27 |
| Orphan files | Files left on disk whose owning session no longer exists: `logs/<session id>.log`, `shell-tasks/<session id>/`, `worktrees/<session id>/`, and plan texts no longer registered in the database. Detection is an **exact session-id allow-list** (all session ids in the database, including archived and subagent threads), never guessed from mtime; `app.log` / `model.log` have no session ownership and are never orphans |
| Discardable data | Files whose deletion loses no session facts: session logs, background command outputs, orphan worktrees, orphan plan texts. Attachments are the lenient tier — deleting them breaks no session content but images in historical messages stop rendering, so they get their own second confirmation. **Not discardable**: `keys.json`, `skills/`, `skills-marketplace/` (historical versions are the rollback assets promised by D12), `workspace/`, and session facts in the database |
| Session deletion | Hard delete: events, approvals, runs, and the thread row are physically removed in one transaction, unrecoverable (currently no delete guard for running / approval-pending sessions) |

## External Protocols and Components

| Term | Definition |
| --- | --- |
| MCP | Model Context Protocol, the standard protocol between models and external tools / resources. CraftWork integrates as a client via rmcp: users configure servers in Settings → MCP (stdio / HTTP / SSE), and once connected their tools enter the registry as `mcp__server__tool` (two-segment naming follows ecosystem conventions) with approvals as usual; stdio servers are local subprocesses (own process group, sanitized environment + user-declared env). Tools may return images (MCP screenshot-style servers): saved into the attachment directory, visible to the model per protocol (Anthropic image-first / OpenAI as a delayed user message), thumbnails in the UI. Protocol projection and configuration model: D16 and `craft-mcp` module headers |
| git engine (craft-git) | The unified crate for in-app Git capability: gix (gitoxide, pure Rust) is touched only by it; git_* tools, environment summary, sidebar status, display names, worktrees, and skill store downloads all go through it — in-app features do not depend on system git (D13); git commands the model / user run through the shell remain shell semantics using the user's git |
| web_fetch | The read-only web-fetch tool (D33): GET, http/https only, risk R3 (outbound network — per-approval on the graded tier, rejected outright in restricted workspaces); HTML is lightly extracted to plain text (script/style stripped, block tags to line breaks, entities decoded, whitespace collapsed); the response is take-limited to 2 MB with a 30s timeout; content-type branches (html extracts title + body / text returned verbatim / binary refused). Fetch only, no search — searching is left to user-configured MCP; included in `EXPLORE_TOOLS`. Outbound discipline (D14) and boundaries: `crates/craft-tools/src/web.rs` module header |
| Shell execution (shell_exec) | The agent's command execution tool: own process group, environment stripped of secret-like keys by blacklist (D18), timeout kills the process tree; commands are interpreted by the user-selected shell, platform default when none is selected (Unix `/bin/sh -c`, Windows `cmd /C`, D25); not an interactive terminal (interactive terminals were removed, decision D1) |
| Diff | The difference before and after a change; code diffs for code, text-level diffs for documents |
| Output budget | The byte ceiling and truncation rules for tool results (D29): the ceiling is **per-tool adjustable** (`Tool::output_ceiling`, default 32 KiB), truncation **happens once**, and the producer declares the dropped bytes (`ToolResult::truncation`). Once declared, the execution exit does not truncate again; undeclared results are truncated at the ceiling with the single "original length" note. Upstream must never derive dropped bytes from "the truncated length" |
| Truncation declaration | When a tool truncates to its own functional limit, it writes the **true dropped byte count** and a model-facing note into `ToolResult::truncation`. Declaration is not a loophole past the ceiling: anything over `output_ceiling` is still trimmed again as a backstop. See D29 |
| Text-level read-write | Modifies Word / Excel content without rebuilding layout; full fidelity of complex styling is not guaranteed |
| Token | The smallest unit of text a model processes, used to meter context and cost |
